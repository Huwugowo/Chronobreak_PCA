# Finding a recorded League match

Product research and design recommendation · 18 November 2026

**Give Match History one place to enter a champion or player, one queue picker, a visible Moment picker, a Saved toggle, and a small Filters menu.** Use a second line only when there is a selection to show. Keep recent matches immediately playable. When someone searches for a play, put the matching event on the match card and let them open the right recording at that moment.

The strongest first release is smaller than this target. Clean up the existing controls, ship readable event presets, and fix how results are explained. The next investment should be **enemy champion and player relationships**. A player remembering “I was Vi, they had Viego” has supplied two excellent clues. Today's search can use only the first.

## What the comparison showed

I inspected the live OP.GG, DPM and DeepLoL desktop profiles. The other rows use first-party product pages or documentation, including the recording apps. The Chronobreak audit follows the current source and screen contract. The order of priorities below is a design judgment that still needs testing with players.

## Where Chronobreak stands

- **Two controls overlap.** “Search matches…” does a case-insensitive substring match on the recording player's champion and recorded game mode. The two adjacent dropdowns also select champion and mode. A player typing an enemy champion or a friend's name into the obvious field can get a plausible-looking empty result. The separate exact Riot ID field sends every partial edit to a query that requires a complete ID. [Toolbar and dispatch](../../app/src/components/LibraryScreen.tsx) · [History query](../../app/src-tauri/src/league_index/query.rs)
- **Combining controls can change their meaning.** Alone, a Riot ID means the person appeared in the match. With an event filter, the same ID must resolve to an actor on the matching event. “Nora was in the game where someone stole Baron” silently becomes “Nora participated in that Baron event.” No label warns about the change. The event controls also expose terms such as `ChampionKill`, `HordeKill` and `acer`. The adjacent Clips screen already uses “Baron steal,” “Pentakill” and “Triple kill or higher.” [History predicates](../../app/src-tauri/src/league_index/query.rs) · [Clips vocabulary](../../app/src/components/ManagedClips.tsx)
- **The data is better in some places and thinner in others than the UI suggests.** The native query already accepts exact queue IDs and a minimum multikill threshold. It has no enemy-champion or date-range predicate. “All roles” means an event actor such as killer or victim. Lane position is a different fact. The recorder currently confirms wins and otherwise emits unknown, even though the outcome menu includes Defeat. An explicit unknown value also differs from a missing result record. [History query](../../app/src-tauri/src/league_index/query.rs) · [Result confirmation](../../recorder/src/league_client/result.rs)
- **The match card and search controller are assets.** One playable match can own several recording parts. Saved includes a match when any part is saved. Events can match a part other than the card's representative. Search retains the last successful page during updates or errors, coalesces typing for 180 ms, and preserves context across a trip to the replay. The normal card opens the video or part chooser. Its existing clip and save actions have their own targets. [Library architecture](../architecture/media-library.md) · [Screen contract](../ui/match-history.md)
- **The count stays the same as the list narrows.** Today it shows all eligible match groups and saved groups. Native results are pages of up to 50 and have a next cursor. Neither the catalog count nor the count with uncertain coverage tells us the number of matches satisfying the query. The zero-results copy currently warns of incomplete coverage even for an ordinary Saved or champion miss. [History screen](../../app/src/components/LibraryScreen.tsx) · [History page contract](../../app/src/leagueIndex.ts)

The searchable-history feature is still a draft. Its older evidence describes a library without search or a persisted index. The current implementation and subsequent shipped features establish a different starting point. Reconcile that draft when adopting the design. ## Which filters earn their place

| Put it here | Include | Reason and boundary |
| --- | --- | --- |
| Search field | Played as, ally champion, enemy champion. Player in game, with player, against player. Queue/mode names also resolve here. | These are clues a person can remember and type. Make the relationship part of the selected label. “Enemy Zed” means anywhere on the opposing team. “With” means the two players were teammates. Premade status would require separate evidence. |
| Toolbar | Queue / mode, Moment, Saved | Queue is a familiar, low-effort cut. Derive options from known library values, with friendly names for verified queue IDs and observed mode as a separate fallback. Saved retrieves a deliberate action. Moment earns permanent space because it can lead to footage. |
| Moment picker | Lead with Pentakill, Quadra kill or higher, Baron steal and Dragon steal. A secondary group offers kills, deaths, assists, other multikills, supported objectives, structures and aces. | Generic champion kills or routine objectives occur in many matches. Their main value comes from choosing the person involved or jumping to a time. Default headline presets to **Anyone** and say so. Offer **Me** or a named actor only when attribution supports it. For example, offer a victim for a death and a credited killer for an objective steal. |
| Filters menu | Recording date, then Result. Start dates with Yesterday, Last 7 days, Last 30 days and a custom range. Show supported result values with a short coverage explanation when needed. | Time answers “the game last night.” Use the local calendar and the match's existing history date. Leave Result secondary while loss confirmation is limited. Keep all matches eligible by default, including ones with unknown outcomes. |
| Test before adding | Played position, exact lane opponent, has clips, has bookmarks, session, patch, duration, account, saved searches | First test position and “has clips.” Position needs reliable per-mode data. Direct lane opponent needs two verified positions and an unambiguous pairing. Clip/bookmark existence needs a reliable group-wide query. Treat session as a browsing/grouping option once its definition is settled. Revisit account for multi-account libraries and saved searches if people repeat complex queries. |
| Leave out of the normal interface | Rank/MMR/LP/region, side or map as separate controls, bans, build/items/runes/spells, KDA/CS/gold/damage thresholds, game-time windows, win streaks, custom Boolean syntax, AI query generation, file size or codec | These serve public scouting, statistical analysis, within-replay investigation, or storage management. Keep descriptive stats and builds on the cards. Consider a niche filter only when repeated retrieval tasks justify its cost and its data is trustworthy. |

## How it should feel

**At rest.** Keep the row in the current bounded Match History rail. In order, show a wide **Champion, player or mode…** field, **Queue / mode**, **Moment**, **☆ Saved**, and **Filters**. Keep the first match near the controls. On narrower windows the compact controls wrap below the text field. Preserve the existing card anatomy and independent Star, clip and More targets.

**Finding a matchup.** Typing `vi` ranks exact champion names ahead of prefix matches such as Viego and Viktor. For a champion, offer explicitly named actions such as **Played as Vi**, **Ally Vi**, **Enemy Vi**. Put the player's own champion first. A recent/played champion list on focus preserves browsing without spelling a name. Typing `kaisa` should find Kai'Sa. Typing a name prefix can surface locally recorded full Riot IDs. Display the tag on every player choice, including two people with the same name. Commit only the identity selected. Keep ordinary champion/mode text search available for people who just type and browse. While a name prefix awaits a player or team selection, keep the previous cards visible and prompt for that choice.

**Combining clues.** After choosing **Played as Vi** and **Enemy Viego**, the field clears for the next entry. A compact removable label below the toolbar shows each condition. One value per category in the first version. Picking another enemy champion replaces that choice. Distinct categories intersect. **Clear all** appears only while filtering. Controls must work with arrow keys, Enter, Escape and Tab. Removing a condition by keyboard returns focus to a sensible neighbor or the field. Selections survive opening a replay and returning to History.

**Finding a play.** Pick **Moment → Baron steal**. The selected label reads **Baron steal · Anyone**. The match card can now show a separate action such as **24:18 · Baron steal · Part 2**. The time shown is the League game clock. Activating it opens the verified recording part at its mapped video position. Clicking the body keeps the usual full-replay behavior. For several hits, show the first one and a compact **2 more moments** disclosure. If a positive observation lacks a usable video mapping, show **Baron steal observed · replay time unavailable** and keep normal playback available. A general event search should work before the direct-seek enhancement ships.

**Filtering by a person and a play.** **With Nora#EUW + Baron steal · Anyone** asks only that Nora was a teammate in a game containing a steal. Choosing Nora explicitly *inside the Moment picker* asks who made the play. **My deaths** is shorthand for a champion kill whose victim is the local player from that recording. A friend who joined the game, the opposing champion, and the event actor are independent criteria. Labels and query behavior must agree even when all three refer to different people.

**Showing results.** With no filters, retain the quiet library summary. With filters, use **3 matching games** if the first and only accepted page contains three groups. For a non-final first page, **Showing 1–50 matches** is truthful. Keep date order, label navigation **Previous** and **Next**, and keep a cursor history scoped to the active query. Put **Showing previous results** beside retained cards while a replacement is pending or fails. A confirmed empty result can say **No matches for these filters** with chips still removable. For an event query with limited evidence, use **No confirmed matches. Some recordings have incomplete event data.** Avoid suggesting a precise number of omitted matches unless the query actually computed it.

## What it takes to build

1. **Polish the existing search.** Keep basic substring matching and rename its placeholder to reflect today's fields until player suggestions ship. Provide one combined searchable champion/mode entry point while preserving picker access. Expose verified queue IDs where a label and inventory are available. Keep Saved one click away. Replace raw event strings with a small preset mapping shared in wording with Clips. For example, a Baron steal is a Baron event with its explicit stolen flag. Pentakill uses the Multikill event and a recorded streak of at least five. Qualify lower tiers with “or higher.” Offer valid event/actor combinations and commit exact IDs only on valid entry or selection. While player presence and event attribution still share one field, label an explicit named-event search as such and prevent an ambiguous combination. Add removable criteria, Clear all, page-aware feedback and accurate empty states. This work can use the existing index and controller.
2. **Make composition truthful across the library.** Extend the typed history query with independent match-participant and event-actor criteria, champion relationship and date bounds. Build bounded local suggestions from the full eligible indexed catalog for the accepted library snapshot. Name normalization helps discover a choice. Compare its canonical champion or recorded full identity when filtering. Use the same checked roster precedence as card rendering, with local team known for With/Against and a known local identity so Ally excludes the recording player. If only the mode is known, a broad mode choice can include it, while a ranked queue choice requires its exact ID. Interpret an inclusive calendar end as the next local midnight, converted to an exclusive instant. Use the existing group date so a game with two parts near midnight appears once. Preserve newest-first indexing and page before rendering. Avoid scanning journal or video files on keystrokes. [Query and scope](../../app/src-tauri/src/league_index/query.rs) · [Schema](../../app/src-tauri/src/league_index/schema.sql)
3. **Return evidence with an event match.** Add a small, bounded set of hit references for the visible page or on group expansion. Each needs the matched part identity, event identity/revision, displayable game time and a validated in-media target when available. Reuse the indexed event-to-replay mapping and normal viewer seek. Only combine duplicate hits across parts when their source identity supports it. Otherwise expose them by part. Batch this work and defer additional hits until expanded. A game remains one search result across parts, including when more than one part observed the same event. Attribute a hit to “Me” only with a resolved actor in that source. Recheck part membership and mapping on open. Match count, hit count, and exported clip count mean different things. [Event queries](../../app/src-tauri/src/league_index/replay.rs) · [Timing model](../architecture/replay-time.md) · [Clip event precedent](../../app/src-tauri/src/league_index/clip_events.rs)

## How to decide if it is better

Compare the old screen and a prototype with the same synthetic library of more than 50 matches. Include two players with the same game name, two different champion relationships, a mode-only recording, an unknown outcome, incomplete event coverage, and a match whose second recording contains the hit. Time from opening History to **the correct playable match or moment**. Also record wrong first opens, whether the player could explain what each selected filter meant, and whether returning from playback lost their place.

| Give the player this task | What would demonstrate success |
| --- | --- |
| “Find the game where you played Vi against a team with Viego.” | They can distinguish their champion from the enemy team without learning syntax. An allied Viego is excluded. |
| “Find last night's game with Nora. You only remember the first few letters.” | They can choose the right full Riot ID and date. Prefix typing never causes a backend-error state. |
| “Find the Baron steal from the game Nora was in. Someone else stole it.” | Match presence and event actor remain independent. The returned time opens the correct part. |
| “Find a saved game beyond the first 50, then return from the replay.” | The search runs across the library, the game appears once, and Back restores the query, position and controls. |
| “Did any of these games have a pentakill?” | The interface distinguishes a confirmed event, a complete search with zero hits, and recordings whose event coverage is incomplete. |

Ship the toolbar and terminology as the first slice. Treat the independent participant/event predicates as the prerequisite for advertising combined searches. Test whether players find a rare play faster with Moment visible before giving any other advanced criterion permanent toolbar space.
