# QB-PERF-005 â€” Whole-application workload characterization

## Purpose

Provide a reproducible Windows measurement of release-app responsiveness and resource use during actual replay workflows, alone and alongside the production native recorder capturing an animated synthetic window. The report identifies meaningful bottlenecks before further optimization. League sessions and League FPS are excluded. Synthetic evidence supports only the measured device, fixture, runtime and workflow.

## Relevant planning-time architecture

Reuse `tools/replay_benchmark/{prepare.ps1,run.ps1,matrix.py,analyze.py}` and the schema-v1 manifest/preparation/matrix contracts. The release app is built with `npm.cmd run desktop:build:benchmark --prefix app`; its benchmark module is feature-gated. The existing bounded observer routes actions through production controllers, uses authoritative requestVideoFrameCallback presentation, and retains action generation, timeouts, errors, source hashes and terminal collector evidence. `run.ps1` owns a Windows Job containing the app and WebView descendants and samples CPU, private/working memory, I/O, handles and threads. Preserve its lifecycle and integrity checks. Minimal observer is the sole accepted campaign profile. Full-observer runs are diagnostic only and excluded from the accepted comparison; the historical paused-seek observer controls do not validate the new search/resize workload.

`app/src/benchmark.ts` declares scenarios and their actions; `App.tsx` owns library/viewer transitions; `ViewerScreen.tsx` executes viewer actions through the persistent playback controller. Extend these owners rather than creating a parallel playback or UI stack. Existing `layout` toggles frontend fullscreen; it does not resize the native window.

The Games input in `LibraryScreen.tsx` coalesces text for 180ms. `HistoryController` serializes the active query and admits only the latest matching generation and library origin. A running IPC query is not actually cancellable. `query_league_history` uses an owned blocking index job; the SQLite cache is disposable and filesystem/journals remain authority. `app/src/dev/libraryBenchmark.tsx` does not exercise this release backend path.

Reuse `tools/native_backend/run_native_fixture.ps1`, its animated WGC fixture, `recorder/examples/native_mp4_probe.rs`, native CFR/NVENC/mux validation and packaged full decode. The production `RecordingEvidence::startup_ready()` already requires capture readiness, first source QPC, surfaced source, encoded frames, mux bytes and positive output time. Production startup waits at most 15 seconds. The fixture probe currently reports process/session construction before that readiness and publishes terminal accounting after `run_for`; it has no live capture-ready handshake for a workload supervisor. `NativeRecorderSession::run_until_stopped` already publishes bounded live evidence at most four times per second. Reuse this evidence contract; do not add per-frame synchronization.

Both the replay CIM GPU provider and native fixture's synchronous `Get-Counter` can stall without a per-call deadline. Replay correctly disables its old provider. Missing GPU observations are unavailable, never zero.

## Scope and non-goals

Add real search-input and desktop-window-resize workloads, a combined navigation/playback/search/seek/resize scenario, a small supervisor pairing that workload with the existing recorder fixture, bounded optional GPU-memory sampling and an integrated report. Retain existing replay and recorder tools as their subsystem authorities.

No League testing, Smite work, broad performance refactor, different renderer, new capture backend, live telemetry service, production always-on profiling, query cancellation redesign, HUD timer optimization or arbitrary absolute CPU target. Existing hardware/runtime restrictions remain unchanged. Export remains covered by its existing separate benchmark; this feature need not duplicate its matrix.

## Exploration findings

The repository already has substantial application and recorder measurement infrastructure. The missing integration is release search, actual native resizing, active-capture overlap and bounded shared GPU-memory evidence. Historical accepted results do not characterize the current release. Old generated bundles are unsuitable: some predate the strict timeline contract, while later v2 media bundles still have obsolete snapshots/events instead of current telemetry journals. Use the complete curated current-format preproduction bundles below. Copy complete bundles without changing media IDs/timelines or source bytes. Provenance is useful; implementation must not require recursively reading old plans.

## Chosen design and rationale

### Workload and fixtures

Add a versioned whole-app campaign spec beside the existing replay schemas, with explicit immutable inputs, ordered alone/capture pairs, five paired repetitions with frozen seed-derived AB/BA ordering (three AB, two BA, or its seed-selected inverse), fixed deterministic actions/seed, cooldown, observer profile, dimensions, DPI/display/runtime/binary/source identity and finite deadlines. Expand launches through the existing matrix planner; extend it minimally only if combined navigation needs additional explicit parameters. A resume executes missing declared slots only and never overwrites a launched/failed result. Any replacement pair receives a new frozen campaign and retains its predecessor's disposition.

Use a sentinel-owned, current-format fixture library and populated offline assets. The immediate application baseline uses the complete curated preprod Swiftplay bundle `fixtures/preprod-library/library/games/1792431584`: strict-v2 metadata, current telemetry manifest, all journal/checkpoint/match/result sidecars, ten participants and 107 in-video events. Its video is a static synthetic H.264/AAC title card and its recorded sidecars retain identities. It can characterize the populated UI/import/query/overlay workload but cannot characterize high-motion gameplay decoder cost or event-to-picture alignment. Keep source bytes read-only, never publish raw names/journals in sanitized reports. The old generated corpus has legacy snapshots/events instead of the current telemetry journal and is rejected as an application fixture even when its media timeline is v2. Stage complete bundles, not three-file subsets.

Seed each disposable Data Dragon cache from the normal preproduction cache at `build/preprod/app-data/ddragon`, then prefetch missing supported fixture icons through the existing resolver contract before freezing its fingerprint. Require ready manifests and PNG-validated cache coverage for all supported champion/item/rune/spell keys used by the exact history and temporal roster/HUD workload, including numeric and recorded-label spell aliases. Freeze the selected version and asset list, record successful asset delivery and image decoding in benchmark-only readiness evidence, and reject an empty cache or unexpected missing image. Merely fingerprinting an empty directory, or reporting ready manifests without icons, is insufficient. The selected preproduction fixture union has ten champions, 88 nonzero item IDs, 13 rune/style IDs and 17 spell keys. Three evolved spell labels are unsupported by the current production manifest resolver; retain their existing explicit placeholders and record them under `QB-LIB-013`. This measurement feature does not substitute icons or reopen that deferred scope. Initial video time zero precedes the first mapped roster at about 24.574s; use a frozen populated timestamp such as 52.433s for the rendered-roster gate rather than asserting ten players in the one-time opening marker.

For accepted combined runs, use the two complete curated preprod bundles (Swiftplay `1792431584` and Practice `1792432630`) copied through the existing preparation tool. This is the user's existing preproduction library, not a claim about a 1,000-game catalog. Preserve all journals, identities, media timelines and explicit unmapped-event states. Expected settled history membership is two games; selected Swiftplay requires nonzero indexed events, ten indexed participants and authoritative video presentation. Before timed actions, bind readiness to the selected media/load generation and require the expected roster and overlay content to be admitted and rendered at a frozen in-video timestamp containing a known event and roster snapshot. Database counts or the initial readiness marker alone do not prove rendered overlay content; retain benchmark-only render/admission evidence for the matching generation. The selected-source payload reports only its current event window, so do not incorrectly require all 107 events at every viewport. A separate bounded indexing diagnostic uses the same sources and a new disposable cache, lasts at most 120s, and reports import/query progress without pooling partial-result semantics into settled-index comparisons. Large-catalog scaling and synthetic high-motion-plus-current-journal generation are separately recorded future work; they are not prerequisites to measuring the existing preproduction workload.

The combined process executes library input bursts, admitted results, opening the selected real video, 30s steady 1x playback, deterministic near/far forward/backward seeks, scrub bursts, real desktop resizes while playing and paused, and return to the library. Freeze order, pace, counts and condition boundaries before accepted runs. Retain at least 40 observations for every reported p95/p99 stratum; label smaller samples descriptive and do not compare their tails. Seek strata retain existing minimum 40 each. Settled-index search traces include coalesced typing at 60ms character intervals, settled queries and clearing. An input burst during normal indexing belongs only to the separate 120s indexing diagnostic, with independently labeled progress/query evidence. Resize uses supported window sizes inside the current work area, alternates at a fixed 250ms minimum pace, waits for geometry/presentation settlement and restores the original size at teardown. Do not issue a new resize while one is unsettled. Each process has eight completed search sequences for each declared search stratum and eight playing plus eight paused resize actions; report pooled event-level tails descriptively only. Each seek run retains 40 valid events in every near/far x forward/backward stratum. Query/resize action settlement has a 10s deadline. Perform normal import as a separate bounded 120s warmup before the settled-index campaign; media readiness retains its existing 30s deadline. Keep a cold-index readiness failure as diagnostic evidence rather than extending that deadline to accept it. Use a fresh process/app-data/WebView root per arm and identical offline assets for settled-index comparisons. Populate each root through the same verified normal import, or an explicitly verified identical cache snapshot compatible with its library root. Bind import completion, cache fingerprint/snapshot and the app-data root in each arm receipt; warming a different root is insufficient. Preconditioning runs the same deterministic import and 30s playback before timed actions. Bind each arm to hashes of the exact launched app, recorder probe, target and helper binaries and their PID plus creation identities. Require equal frozen source/binary identities and equivalent completed cache state across the pair. Freeze a minimum 30s inter-arm cooldown and record CPU/power/display state for the last 10s; mismatch or background interference invalidates the pair. The same sequence and input identities run in both conditions. Comparisons use paired per-process differences and a paired bootstrap over the five pairs; events within a process are correlated, not independent trials. Report the resulting uncertainty rather than a precise causal estimate from five processes.

### Search measurement

Add `library_search` and combined-scenario actions to the existing benchmark bridge. Dispatch an InputEvent into the actual search input (normal onInput handler), so the production debounce, query scheduling, backend and checked result admission execute. Use bounded benchmark-only action/generation IDs; record input, scheduled/coalesced, actual dispatch, backend completion, checked admitted/superseded outcome and the first post-admission paint opportunity. Keep dispatch-to-result and last-input-to-painted-result distinct. A paint opportunity is two animation frames with generation/origin revalidation, not proof of physical screen presentation.

Add narrow benchmark-gated backend timing around history query work only when needed to distinguish queue/SQL/IPC costs. Never attach raw query text, player identities or unbounded result arrays to reports. Report dispatched, replaced-before-dispatch, completed-but-superseded, admitted and errored counts separately. Do not call a suppressed stale completion a cancelled running query. A stale page must never be reported as matching the current filter. Keep production debounce and serialization policy unchanged.

### Native desktop resize

Add `desktop_resize` actions using Tauri's native window size API through a benchmark-only seam. Record request, matching native resize event/physical geometry and the first authoritative current-generation media frame after geometry settlement when playing. Paused resize reports geometry and UI paint latency without inventing a newly presented frame. Retain element/load identity so a resize-induced decoder replacement, error or recovery is visible. Preserve display scale and convert logical/physical sizes explicitly. Bound each action and restore geometry even on cancellation/failure. Existing layout actions remain distinct.

### Complete seek evidence before benchmark teardown

The current controller may resolve its seek promise on authoritative presentation before the independent native `seeked` observation. A final scrub can therefore pause and release the viewer while that observation is pending. In `ViewerScreen.tsx` benchmark-only action completion, wait with a finite deadline for both matching-generation dispatch-to-native-seeked and authoritative-frame observations (either arrival order), or an explicit terminal failure/supersession, before reporting settlement and releasing media. Use existing observer/action ownership and timeout helpers; do not change production seek-promise semantics without separate evidence. Preserve missing-phase rejection in `analyze.py`. Test both event orders, final-action teardown, supersession, timeout and disposal; a missing observation must fail rather than being fabricated or tolerated.

### Recorder contention supervisor

Add one thin campaign coordinator at `tools/replay_benchmark/run_whole_app.ps1`, with its versioned specification at `tools/replay_benchmark/whole-app-campaign.schema.json`. It owns only its generated fixture/probe/helper processes, invokes the existing replay runner and native validation, and writes a bounded cross-run receipt. Do not invoke the League/tray capture campaign.

Expose a feature-gated `whole-app-fixture` probe mode, isolated from ordinary production startup. Add a narrow library fixture entry point around the crate-private live native ownership path so the example can use it without broadening the production recorder API. The coordinator creates a new sentinel-owned control directory with exclusive ready/progress/stop paths and a random session nonce; the probe refuses pre-existing receipt/stop files and validates the nonce. Publish bounded JSONL ready/progress receipts with strictly increasing sequence, source/encode/mux counters, QPC, monotonic elapsed and UTC at no more than 4Hz. The coordinator writes one exclusive matching stop request after the replay terminal/collection receipt; the probe polls it at the existing evidence cadence and requests cooperative stop. Partial/oversized/malformed/stale control data fails closed. Stop requests and process finish have finite 15s and 30s deadlines respectively, followed by kill/reap of only the owned job. Expose readiness from the native session's existing bounded live-evidence path. Readiness must satisfy the same `startup_ready()` predicate, with a 15s startup deadline. It cannot be based on spawn, stdout STARTED, output-file existence or one source frame. Preserve fixed-duration probe behavior for existing callers; a controlled fixture mode can request graceful stop after the workload with a hard overall deadline and the normal finalization path. Avoid a new general recorder API: use a narrow feature-gated fixture harness around the existing ownership/evidence path. Keep strict frame accounting, existing failure limits, output validation and process cleanup. If graceful stop changes tick-count expectations, validate the actual committed stop interval with the same scheduled=submitted=completed=muxed invariant rather than relaxing the fixed-duration checks.

The coordinator uses one monotonic clock for received ready/progress, replay process/workload boundaries and stop, with UTC anchors for audit; retain source QPC separately. Entire measured workload must be inside the established active-capture interval, not merely intersect process lifetimes. Require monotonically advancing source/encoded/mux counters across every individual timed workload window plus successful terminal accounting/full decode. Bracket every window with progress receipts that establish advancement inside that window; aggregate advancement across the process is insufficient. Require progress observations on both sides of each measured boundary, with no receive gap over 2s during any window; rejected gaps remain visible. The coordinator's process topology is explicit: existing replay Job owns only app/WebView descendants; a separate owned capture Job contains probe/native worker and ffmpeg, another owned Job contains the synthetic target, and a final Job contains the GPU helper. Resource samples are attributed by PID plus creation identity; totals do not include target/helper in app or recorder sums. A missed readiness deadline, stalled progress, partial overlap, recorder error, changed input, media failure or descendant leak invalidates the pair. On any failure preserve raw artifacts, cooperatively stop and then finitely terminate only owned jobs. Keep the synthetic target visible and record geometry/device; never capture the desktop or an unrelated window. Match the synthetic target's animation in the alone arm too, so recorder contention is the changed condition. Reserve a fixed nonoverlapping physical-pixel rectangle for the target and a separate work area for all app resize sizes; prefer separate monitors. Record both HWND bounds, visibility, DPI and monitor identity throughout, and invalidate on minimization, overlap, bounds drift or display change. The target may be always-on-top only inside its reserved area, never over the measured app. If the current display cannot fit the supported app minimum plus target without overlap, require a suitable display layout rather than accepting occluded evidence.

### Bounded resource evidence and report

Keep app process-tree and recorder/ffmpeg resource totals separate; record the synthetic target and measurement helper as their own overhead. Reuse the existing bounded process-sampling mechanisms for each owned job and leave the native fixture's old synchronous `-CollectResources` GPU path disabled. Use timestamp-aligned samples and preserve startup, steady playback, input, seeking, resizing, indexing and cooldown windows. Report median/p95 normalized machine CPU, total CPU time, private/working memory high-water marks, process churn and within-run retained memory growth. Do not infer a leak from one high-water mark; compare settled post-cycle samples and source/card/query counts.

GPU allocation sampling must run out of process, outside timing-critical app/recorder loops. Use a Windows PDH helper with English counter binding (PdhAddEnglishCounter) for GPU Process Memory Dedicated/Shared Usage, so display-language differences do not require guessed translated counter names. Implement it beside the existing collector helpers; keep counter ownership inside that helper. One owned helper at most, one pending query, bounded output, a 2s response deadline and finite shutdown. Query once per second when available; on stall kill/reap the helper, mark the affected remainder unavailable and continue core measurement. No repeated relaunch storm, synchronous Windows counter call in the main collector, fabricated zero or physical-VRAM claim from process-allocated dedicated/shared bytes. Preserve individual PID/creation identities to reject reuse and separate app, recorder, target and helper allocations. Deterministic tests must simulate timeout, malformed/oversized output, absent/localized counters, PID reuse and forced teardown. Live completion requires successful bounded dedicated/shared allocation sampling on a compatible Windows host across both measured conditions. If unavailable, retain the feature as non-done with GPU characterization environment-blocked; no silent waiver or zero substitution.

Extend the existing analyzer/report model rather than aggregating unvalidated files by hand. Report each pair, condition/window sample counts, input identities, invalid reasons, result distributions, source integrity, recorder continuity and missing evidence. Search input/dispatch/backend/paint and native resize/presentation latencies retain their different authorities. Profile indexing churn from dispatch, supersession and backend timing. HUD work is investigated only if traces identify meaningful overhead. Every actionable finding is assigned to an existing feature, a focused new draft, a documented limitation or an explicit request for more evidence.

## Rejected alternatives and planning decisions

- Rebuilding a generic benchmark framework duplicates established lifecycle and media-safety mechanisms.
- Dev-browser/local-array filtering cannot establish production search latency.
- CSS fullscreen cannot substitute for native window resizing.
- A capture process or output file cannot prove active encoding/mux overlap.
- Direct SQL seed data alone skips the normal import/admission path and is not accepted end-to-end evidence.
- An unbounded counter provider cannot join core sampling. An unavailable counter is preferable to a hung or biased run.
- Tiny fixed CPU improvements and unsupported League FPS extrapolations are not acceptance goals.

## Performance and reliability gates

This feature characterizes the app; it does not promise an arbitrary CPU percentage or instantaneous result on every device. Preserve existing validity gates: zero required event loss, valid action/generation outcomes, no hidden/minimized measured UI, no timeout/recovery/media/source-integrity error, complete bounded collector finalization, no owned descendant leak, normal recorder frame accounting and successful output decode.

Use the existing comparison repeatability bands: max(resolution floor, three times baseline MAD), with 5ms latency, 0.1 normalized CPU percentage point, 8MiB memory and 1% byte/count floors. Flag an unfavorable change exceeding both this band and 5%; treat new errors, capture stalls, source mutations, event loss or sustained retained-growth signals as material regardless of band. These are evidence/disposition rules, not mandatory optimization targets. If the measured app is already efficient and no material bottleneck appears, the report may conclude that no further optimization is justified. Do not weaken criteria to accept failed measurements.
