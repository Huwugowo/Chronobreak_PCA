# QB-DIST-004 Windows installer and downloadable release

## Purpose

Ship one Windows x64 setup executable that installs the Chronobreak desktop, background recorder, and locked media tools together. A player can record a League match, open and seek the replay, and export a playable clip on a supported machine with no development tools. An update or uninstall must protect capture finalization, settings, recordings, and clips.

## Relevant architecture and exploration findings

- The previous Tauri build generated MSI and NSIS installers. Both omitted the recorder. The portable desktop PE imports no app-local DLL, while the standard recorder build imports `VCRUNTIME140.dll`. The NSIS package defaulted to a per-user install at `%LOCALAPPDATA%\League Replay`; the MSI used Program Files. The generated NSIS script can invoke a previous uninstaller, delete a different Run value, and offer recursive app-data deletion. The [readiness inspection](../reviews/windows-installer-readiness-2026-10-26.md) records the historical packages.
- The desktop supervisor in `app/src-tauri/src/recorder_supervisor.rs` starts the literal sibling `recorder.exe`. Both executables consume `resources/media-runtime` beside themselves, validated against the embedded `media-runtime/runtime-lock.json`. `tools/media_runtime/stage_release.ps1` already assembles and verifies this layout in an isolated build directory.
- The version-independent recorder-control lease excludes other sessions for the same Windows user until the production recorder exits. The status pipe is observational. The existing tray Quit path waits for shutdown/finalization. Login registration is enabled by the user and owns exactly HKCU `Software\Microsoft\Windows\CurrentVersion\Run`, value `Chronobreak Recorder`, REG_SZ containing only the quoted absolute recorder path. See [recorder supervision](../architecture/recorder-supervision.md) and the [media runtime contract](../architecture/media-runtime.md).
- DIST-002 owns supervision and login acceptance. DIST-003 owns the complete installed settings contract. The installer treats the existing settings file and media as user data and ships only after both contracts pass their own gates.

## Scope and non-goals

Publish one current-user x64 NSIS installer with a Start Menu shortcut, Windows uninstall registration, and WebView2 bootstrapper support for online installation on supported Windows. Use a monotonic Windows-compatible version above the historical beta for the first candidate, preserve `com.leaguereplay.desktop` and the legacy installer identity for detection, and label the download Chronobreak. Preserve the stable default install path. Support in-place migration from a positively identified historical per-user NSIS beta at that path. Give a clear, pre-mutation failure for MSI, custom-path, unrecognized, or unsafe layouts. A portable ZIP may exercise the paired payload independently.

Keep machine-wide installs, offline WebView2 installation, automatic updating, additional architectures, capture backend changes, and settings redesign outside this feature.

## Chosen design and rationale

### Build and deliverable

Use the locked Tauri CLI and a Windows NSIS custom template. Set Windows bundle targets to NSIS. A Windows-scoped `beforeBundleCommand` stages the release payload after Tauri builds the desktop executable. It builds the locked recorder for x64 MSVC with a statically linked Visual C++ runtime, supplies both same-run executables to the existing stager, verifies the runtime, and produces a file inventory and hashes including the application, recorder, runtime contents, and any required app dependencies. It then builds the setup coordinator against the expected payload manifest digest. Keep the coordinator hash in a separate installer-envelope inventory to avoid a self-referential digest. Require a clean checkout, known source revision, and locked build inputs in the candidate build entry point. Embed the revision in both executables and compare their reported identities before bundling, then retain the revision, runtime ID, version, and file/installer SHA-256 values. Build the coordinator with the same static CRT policy. Inspect all release executable imports and fail the candidate if it depends on a separately installed Visual C++ runtime or an unstaged application DLL. Keep the no-bundle desktop development path. [Tauri installer customization](https://v2.tauri.app/distribute/windows-installer/) [Microsoft C++ deployment options](https://learn.microsoft.com/en-us/cpp/windows/deployment-in-visual-cpp)

The NSIS template owns UI, WebView2 prerequisite handling and execution of the native setup coordinator. Extract to a unique user-private, reparse-free scratch location, verify the packaged coordinator and expected payload inventory, and keep opened identities pinned where used. Scope authenticity claims to a trusted installer and separately published installer checksum or signature; the file list detects substitution within that trusted build. Render the custom template without Tauri's default payload copy, predecessor uninstaller invocation, automatic execution of the desktop, broad Run cleanup, force-close, or AppData deletion paths. The coordinator owns install, upgrade, product shortcut and uninstall registration changes, and uninstall. Fetch or install WebView2 before beginning any Chronobreak replacement. A prerequisite failure leaves Chronobreak untouched.

Keep the final app and recorder directly beside each other in the stable product root. Extract the final installer offline and compare the exact installable file inventory and hashes against the staged tree, including the coordinator and all runtime notices. Fail packaging for omissions, extra payload, revision mismatch, or unexpected installer rules. Publish only a verified setup artifact and its checksum through an approved download host. Retain the locked runtime notices and make exact corresponding source (including patches, build scripts and applicable linked dependencies) available alongside the binary download. Check the final links and note Windows, WebView2 connectivity when needed, and the supported NVIDIA recording path. Document signing status for the actual release. Keep publishing and any repo visibility change explicit. [GNU GPLv3, section 6](https://www.gnu.org/licenses/gpl-3.0.html#section6)

### Exclusive maintenance and legacy entry

Add a small Windows setup coordinator with reusable install-guard code for the desktop and recorder. Use a SID-scoped lock file outside the replaced tree, with shared use for installed processes and exclusive use for setup. Identify the installed path from validated fixed path and product state, including the interval while install metadata is being recovered. Acquire shared use before accessing release resources or starting/configuring a recorder. Retain it through actual process exit and worker/finalizer shutdown. Portable processes continue to use their existing path and ownership contract. For a set of overlapping setup/launch operations, use a consistent guard acquisition order and nonblocking attempts with bounded retry on user request.

Install, update, and uninstall take the exclusive guard and acquire the existing production recorder file lease without starting a status server. Hold them through verification, commit or rollback. An occupied lease, shared guard, or unidentifiable owner aborts before altering the installed payload. Ask the user to close the desktop and use tray Quit, including in another session when necessary, then retry after actual exit. Status failure, timeout, and disappeared tray icons never authorize proceeding. Do not terminate recorders, kill app processes, or schedule replacement on reboot. Silent execution returns a nonzero diagnostic on contention.

Identify the supported beta with exact inventory and payload fingerprints from the historical installer, known per-user registration, and verified root. Require no foreign content, reparse points, or config/media directories beneath a root that will be replaced. Historical beta processes do not use the new guard. Before admitting the legacy migration, confirm in an isolated Windows fixture that non-followed handles can deny new execution while permitting same-volume rename. Acquire and retain those handles for every legacy executable from validation through settlement, validate identities and detect existing image mappings or running processes. Fail before mutation if access, process identity, or the execution barrier cannot be established. Installation does not invoke legacy uninstall code or adopt an existing portable recorder or unrelated registration.

### Install, upgrade and recovery

Stage and verify the whole candidate on the same local NTFS volume before moving the stable root. Validate the parent and every path boundary against reparse/redirected paths. Store the transaction record in a bounded, user-private sibling directory with fixed leaf roles, never paths accepted from record contents. Retain the exact old and candidate manifest identities and prior product metadata. Persist intent before each destructive step and flush the journal. Recovery treats the record as intent and verifies actual stable, staged and prior trees by inventory, identity and hash before choosing completion or rollback. Refuse ambiguous states and retain evidence for repair.

On upgrade, move the old tree to a same-volume previous directory, then move the complete staged tree to the stable path. These are two separate renames. Exclusive maintenance blocks participating launches and the legacy launch barrier covers the old tree. The stable name can be briefly absent, including after abrupt interruption until setup repair. No running process may observe a mixed tree. Before commit, verify files and exact shortcut/uninstaller ownership at the stable path. Any handled failure before commit restores the verified prior tree and metadata. If interruption or a secondary filesystem error prevents immediate restoration, retain the prior tree and refuse further launch/mutation until verified repair. A failure cleaning up after a verified commit keeps the new install active and leaves any unresolved material for repair. Never delete retained input as a substitute for restoring it.

Before each move or deletion revalidate the exact allowlisted members and file identities against the transaction state. Cleanup removes individually verified files and empty owned directories. Unexpected or locked files stop that cleanup and remain intact. Keep configuration outside the payload and perform no installer writes to it. An owned Run value at the stable quoted target stays unchanged during a successful update and a rollback. Absent registration stays absent; foreign or unreadable ownership is surfaced without rewriting it. Commit the version change and retire the beta only after the new payload and metadata verify.

### Uninstall

Use the same maintenance guards and ownership checks. Remove only verified owned installed files, product shortcuts and metadata, and the exact owned Run value. Remove directories only when empty. Re-read the typed Run value at mutation under the guard shared by all supported app settings writers; leave absent or foreign values alone and report unreadable ownership. Retain uninstall registration until file and registration work has completed or is recorded for retry. Never recurse through either AppData or library directories. Preserve config, all user recordings/clips, and any other files even when a selected library is under the product root. Validate this explicitly with controlled fixture data.

## Rejected alternatives and planning decisions

- Publishing both installer formats doubles lifecycle and migration verification. Use one NSIS setup and detect the incompatible per-machine layout before making changes.
- A Tauri sidecar or copying the recorder under resources would change the established sibling contract. A default template with only an extra file would still allow unsafe replacement and uninstall paths.
- In-place overwrites, forced process termination, status-only tests for ownership, and pending-delete-on-reboot actions can lose capture or pair incompatible files. The entire release is staged before any swap.
- The portable ZIP is a useful local release artifact and payload check. Installer acceptance still depends on installed lifecycle and an actual match.

## Milestones

1. Produce and inspect a candidate installer payload with the release build hook, native helper identity, shared runtime, and version/revision checks. Keep candidates local and block setup mutation until the maintenance gate exists.
2. Implement and verify Windows guard acquisition, actual exit handling, and the historical beta launch barrier against isolated fixture processes. Verify the legacy eligibility predicate and refusal cases before enabling migration.
3. Implement guarded fresh installation, verified swap with repair, and conservative uninstall. Validate failure injection, restart state, data preservation, shortcuts/registry, and setup exit codes in a dedicated test profile.
4. After the supervision/login and installed-settings gates pass, run the clean-machine acceptance matrix, document supported environments and recovery, then prepare the public release assets and verify their download links.

## Verification design

- From a clean Windows x64 checkout with the documented build prerequisites and locked runtime staged, run `npm run tauri --prefix app -- build` through the configured production bundle path. Release automation adds CI/locked flags and records all inputs. Run the applicable [project verification](../development/VERIFICATION.md), including packaged layout/hash checks, generated media smoke with sanitized PATH, and recorder diagnostics from the extracted payload.
- Inspect generated NSIS instructions and extract the built setup without running install actions. Compare all intended bytes against the verified staging manifest, including recorder/app source revision reports and locked runtime hashes. Test that missing/tampered components and unexpected file entries refuse publication or mutation.
- With disposable Windows profiles/install roots, validate fresh setup, current-version repair, detected supported beta, rejected MSI/custom/foreign layouts, destinations with no system FFmpeg/ffprobe, alternate Windows sessions, blocked app/recorder, absent/foreign/matching Run values, WebView2 failure, and config/media paths under and outside the root. Compare exact before/after config and recording/clip hashes and registry values. Fault-inject disk/handle errors and interruption before/after each rename and metadata write. Verify recovery is idempotent and no unexpected files or registry entries are removed.
- On dedicated supported Windows without Rust, Node, or system FFmpeg/ffprobe, download and run setup and launch from its shortcut. Confirm one tray recorder, user-controlled login startup with actual sign-in, and a real League match through capture/finalization, replay seek and playable clip export. Upgrade the admitted beta after exercising a blocked update during recording and successful tray Quit/finalization. Uninstall with a dedicated library and verify binaries and exact registration are gone while media, clips and settings remain. Save setup logs, version/hash inventory, redacted registry evidence, and media validation output.

## Performance and reliability gates

Guard work is limited to startup and maintenance, with no resource checks or new work in the capture loop. Verify that no installer writes occur during capture or finalization, that the recorder's actual completed media decodes after the user quits, and that competing launches cannot change the installed pair during transition. Exercise repeated lock contention with bounded waits and no processor-heavy polling. Require recovery to retain a complete eligible old tree or publish a complete verified new tree. A stable path absent after an interruption must be repairable using the same setup, with the retained prior tree verified before any destructive action. Failed cleanup retains unknown material and never touches user media.
